# Backlog

## この backlog の運用ルール

### バージョンと見出し

- バージョン番号は SemVer に従う（機能追加 = minor、修正のみ = patch）。major は都度判断する（該当しうるのは代替なしで機能を大きく削る場合。多少減る程度や同等の代替があるなら minor で扱う）
- 見出しはバージョン単位で切る。リリースとして出す価値のあるまとまりで区切り、goal の大きさには合わせない
- バージョン見出しが大きくなったら、配下にサブ見出しを立てて塊ごとに分ける。**サブ見出し 1 つが 1 goal の実行単位**（数コミットで終わる大きさ）。小さいバージョンならサブ見出しを作らず、バージョン見出しごと 1 goal にしてよい
- **未リリースのバージョン番号は挿入・繰り下げしてよい**。v1.8.0 と v1.9.0 がある状態で v1.8.0 直後にやりたい作業ができたら、それを新 v1.9.0 とし、既存 v1.9.0 を v1.10.0 にずらす。タグを打ったバージョンは動かせない
- 番号が決まらないタスクは番号なしの見出し（例: `## SDK 更新時（バージョン非依存）`）に置く。次のリリースへ同梱するか独立バージョンにするかは、タグを打つときに決める
- 挙動が変わらない変更（リファクタ・テスト・ドキュメント）だけでバージョンを刻まない。次の機能・修正リリースに同梱する
- 修正・保守の量が多い時は、1 バージョンに詰め込まずテーマ別に複数の patch バージョンへ分散してよい（リリース単位が読める大きさに保つため）

### タグと CHANGELOG

- タグと GitHub Release は 1:1 で作る。リリース実行手順（MARKETING_VERSION 更新・tag・gh release）は別途 release-flow に従う
- CHANGELOG は**リリース時にまとめて書く**（`[Unreleased]` は使わない）。そのバージョンの項目が全て `[x]` になってから `## X.Y.Z — YYYY-MM-DD` に書く。`CHANGELOG.md` と `CHANGELOG.ja.md` の両方を同じリリースで更新する
- **書くときは各 commit の diff を読む**。backlog のタスク文をそのまま写さない。内部整理のつもりの項目でも、エラー文言等のユーザー影響が出ることがある
- 同一バージョン内で「A を作って後で X に変えた」場合は、A に触れず X だけを書く。前のバージョンの A を変えた場合は変更として書く
- 完了項目は `- [x]` にして残し、そのバージョンをリリースしたら見出しごと削除する（内容は CHANGELOG と commit に残る）。**削除は明示指示があるときだけ**

### 項目の登録判断

- audit / レビュー findings の採用・不採用は `/design-decision`（`docs/rules/principles.md` の基準）で判断する。トレードオフがあって基準で決められないもの（UX 方針・情報管理方針・互換性許容）だけユーザーに相談する
- 不採用にしたものは「登録見送り」節に理由付きで残す。ただし**再判断トリガーを書けるものだけ**残す。トリガーを書けない不採用は残さない
